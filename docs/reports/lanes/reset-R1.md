# Lane reset-R1: npm dependencies follow real imports in the registry

## Cause

`packages/registry/src/build-registry.ts` gave every file under
`packages/shared`, `icons`, `motion` and `styles` to one `core` item, and
every component depends on `core`. Components import shared code through the
barrel `@the-system/shared`, which the registry rewrote to
`ds/shared/index.ts`. That barrel re-exports every shared file, so the walk
reached `shared/date.ts`, the core item collected `@internationalized/date`,
and `ds add kbd` installed a calendar library. The snapshot in
`packages/cli/src/main.test.ts` had been updated by hand to match.

## Change

All in `packages/registry/src/build-registry.ts`. No component source changed.

1. Barrel split. Before a file is walked, each named import or named
   re-export of a workspace package barrel made only of `export * from`
   lines (`@the-system/shared`, `@the-system/motion`) is rewritten into one
   statement per source file, for example
   `import { shortcutKeys } from '@the-system/shared/shortcut'`. Names are
   mapped to files with the TypeScript AST, following `export *` and local
   `export { name }` of imported names. A name exported from two files, or a
   name the barrel does not export, fails the build. Namespace and side effect
   imports of a barrel are left alone (none exist). The usual rewrite then
   turns these into relative paths, so installed code imports files one by one
   and the shared and motion barrels never ship.
2. Lib items. After the walk, any core file whose import closure reaches an
   npm package (peers `react` and `react-dom` excepted) leaves core and becomes
   its own `registry:lib` item named `<package>-<file>`. Today that is only
   `shared-date` (`ds/shared/date.ts`, `@internationalized/date`, depends on
   `core`). Items whose files import it list it in `registryDependencies`
   through the same owner graph as any other cross item import. Theme takes
   the same route, in case it ever imports such a file. Core now has no npm
   dependency. No hand kept list.

Tests added in `packages/registry/src/build-registry.test.ts`:

- an item whose files do not import `@internationalized/date` does not list
  it; the install closures of kbd, button, list and toast neither list it nor
  ship `shared/date.ts`, `shared/index.ts` or any file that names the package;
- calendar, date-field, time-field and date-picker reach it; `shared-date`
  holds only `ds/shared/date.ts` and depends on core; core lists no npm package;
- no item lists an npm package that none of its own files import (TS imports
  or CSS `@import`), which is stricter than "its files or its registry
  dependencies' files";
- no item ships `shared/index.ts` or `motion/index.ts`, and Kbd imports
  `../../../shared/shortcut`.

The `add, react` snapshot was regenerated by the test run (`-u` on that test
only). The only change is the date library leaving `dependencies` and the
`install` line. README item table and a paragraph on the split updated.

motion and motion helpers barrels left; nothing else moved).

## Proof

- `npx vitest run packages/registry packages/cli`: 3 files, 37 tests pass.
- `npm run typecheck`: clean. `eslint packages/registry/src`: clean.
- `npm run gen` twice: the second run leaves no diff in `packages` or
  `apps/docs`.
- Install proof in a scratch folder: the closures of kbd, button, calendar,
  date-picker, time-field, list and toast were written into empty apps and
  type checked alone with `tsc --strict` (only a `*.css` module declaration
  added, as a bundler supplies). Zero errors each. Only the calendar,
  date-picker and time-field apps contain `shared/date.ts` or any import of
  `@internationalized/date`.
- `ds add <name> --dry-run` for kbd, switch, button, color-picker, list and
  toast lists no date library; calendar, date-field, time-field and
  date-picker list it. color-picker, a React Aria user, lists
  `react-aria-components` and nothing new.

## Consumer examples

`examples/consumer-next` and `examples/consumer-vite` (not under `apps/`) use
the workspace packages (`@the-system/react` and so on) directly. Their `check`
scripts are `next typegen && tsc --noEmit` and `tsc --noEmit`: they type check
the app against the workspace source and never read the registry, so they do
not cover this change. The scratch install proof above is the check that does.
